# 0011. Asset pipeline and model loading

- **Status:** Proposed (implementation planned as content-track milestones C1–C3, see
  [ROADMAP](../ROADMAP.md#content-track-parallel-from-m3-onward))
- **Date:** 2026-10-27

## Context

Every unit is still drawn as a coloured box. Real models and textures should start arriving
now (see the [art guide](../art-guide.md)), one at a time, from people who are not
programmers, and without destabilising the engine. PLAN.md §4.3 already chose glTF 2.0 with
meshopt and KTX2, a placeholder asset provider and a `tools/asset-pipeline`, but not how
they fit together.

Forces and constraints:

- **ADR-0004:** three.js only in `apps/client/src/render`. **ADR-0002:** art must never reach
  the simulation. **ADR-0006:** what a unit looks like is data, not code.
- Instanced rendering: one draw call per unit type (per part). Models must be normalised to
  a few meshes before they are instanced.
- Each match gets a fresh WebGL context (`GameSession`), so GPU objects die with the match.
- The server caches everything under `/assets/` forever (`immutable`), so files there must
  have content-hashed names.
- Contributors make mistakes that are easy to catch by machine: wrong scale, wrong origin,
  huge textures, missing licence. These should fail in `pnpm check`, not in a playtest.
- Supply-chain policy (`pnpm-workspace.yaml`): few, aged dependencies.

## Decision

### 1. Data names the model; assets live outside the data

- `UnitDef.visual` and `FeatureDef.visual` gain an optional **`model`**: an asset id, by
  convention the content id (`dir_lancer`). No `model` means the placeholder box, so models
  arrive one unit at a time. `visual.size` stays: it is the fallback and the reference size
  the pipeline checks models against.
- The reference is part of the ruleset (and its hash, ADR-0009). The model **bytes** are
  not: peers with different art never desync, because art never reaches the simulation.

### 2. One source folder, one generated output

```
assets/                              authored, committed (game-ready files, not .blend/.psd)
  models/dir_lancer.glb              plain glTF binary, made per the art guide
  models/dir_lancer.asset.json       sidecar: author, licence, source URL, notes
  models/dir_lancer_team.png         optional team-colour mask
  textures/terrain/…                 later: tileable terrain sets
  CREDITS.md                         generated from the sidecars

apps/client/public/                  generated by the pipeline, git-ignored
  assets/models/dir_lancer.3f9a2c1b.glb   content-hashed, served immutable
  asset-manifest.json                     id → url, bytes, triangles, parts, bounds (no-cache)
```

- Every asset needs a sidecar with an allowed licence (`CC0-1.0`, `CC-BY-4.0`,
  `CC-BY-SA-4.0`, or the project's own art licence once chosen). No sidecar or a
  non-commercial licence fails the check. `CREDITS.md` is generated from the sidecars, so
  attribution can't drift.
- Large working files (`.blend`, `.spp`, `.psd`) stay out of the repository, or go in Git LFS
  if they are ever wanted there.

### 3. `tools/asset-pipeline`: validate, normalise, emit

A Node workspace package (`@stratcom/asset-pipeline`), built on **glTF-Transform**. It may
import `@stratcom/data` to know every content id and `visual.size`. Two commands:

- `pnpm assets:check` runs the validation only. It is part of `pnpm check` and CI.
- `pnpm assets:build` validates, normalises and writes the output and the manifest. It runs
  before `pnpm dev` and `pnpm build`.

Validation (errors fail the build; warnings print):

| Rule                                                                            | Level           |
| ------------------------------------------------------------------------------- | --------------- |
| File name is a known unit or feature id; a `visual.model` without a file        | error           |
| Sidecar present, licence allowed                                                | error           |
| Ground origin: lowest point within 0.25 m of y = 0                              | error           |
| Size within 25 % of `visual.size` (warning); off by more than 4× (cm/mm export) | warning / error |
| Centred on the origin (bounds centre within 10 % of the footprint)              | warning         |
| Triangle budget by role (art guide §3); 4× over                                 | warning / error |
| Textures square, power of two, at most 2048                                     | error           |
| Materials: more than 1 is a warning, more than 4 an error                       | warning / error |
| Node names: only the documented part names (`turret`, `barrel`, `muzzle`, …)    | warning         |
| Skins and animations (not supported yet; ignored)                               | warning         |

Orientation (+Z forward) cannot be detected reliably, so the art guide's viewer check stays a
human step.

Normalisation: apply transforms, weld and deduplicate, prune unused data, and join every
static mesh into one mesh per material. Named parts stay separate, with their pivot recorded.
Output files are named by content hash.

### 4. Client: bytes outside the renderer, GPU objects inside it

- **`apps/client/src/assets/`** (no three.js) loads `asset-manifest.json`, fetches the models a
  match needs during the loading screen (a real progress step: "Models 12/15, 3.4 MB"), and
  keeps the bytes in a cache that outlives a match. A missing or broken file logs a
  **warning** and the unit keeps its box; a match never fails to start over art.
- **`apps/client/src/render/models/`** turns bytes into GPU objects for the current context:
  three's `GLTFLoader` (from `three/examples/jsm`, no new dependency), `MeshoptDecoder` and
  `KTX2Loader` from C3. It produces one **`UnitModel`** per type: a list of parts, each with
  geometry, material and pivot. Everything is disposed with the session.
- **The placeholder provider becomes an interface.** `UnitLayer` asks a `ModelProvider` for
  each unit type and gets either the loaded model or the generated box, and creates one
  `InstancedMesh` per (type, part). Everything the layer does today (interpolation,
  build-progress height and grey tint, selection rings, the strategic-zoom fade) keeps
  working unchanged on models.
- **Team colour** is a small extension of `MeshStandardMaterial` (via `onBeforeCompile`)
  that mixes the per-instance colour into the base colour where the team mask is white. A
  model without a mask is tinted as a whole, at reduced strength, so ownership stays
  readable.

### 5. Phases

- **C1, Foundation (before M5).** Everything above except articulation and compression, plus
  one real CC0 or self-made model that proves the path end to end.
- **C2, Articulation (with M5).** Named parts become their own instanced meshes; turret yaw
  and barrel pitch come from the snapshot once weapons aim; `muzzle` points come from the
  manifest for muzzle flashes and projectiles.
- **C3, Optimisation (before the v0.1 release, M7).** meshopt compression; KTX2/Basis
  textures (encoder choice open, see below); a download-size budget reported in CI.

## Consequences

- Adding a model needs no code: a `.glb`, a sidecar, and `model: "<id>"` in the unit data.
  Mistakes are caught by `pnpm check` with a message that names the file and the rule.
- Art can never cause a desync or a failed match start; the worst case is a grey box.
- A new tool package and **glTF-Transform** as a dev-only dependency (an aged version, per the
  supply-chain policy). No new runtime dependency: the loaders ship with three.
- Each named part costs a draw call per type, so articulation is kept to the few parts that
  really move.
- Skeletal animation does not fit hardware instancing well. Walkers will need vertex
  animation textures or rigid part animation; that is an open question, not part of this ADR.
- `visual.size` remains the source of truth for footprint, selection and fallback, so models
  and data have to agree. The pipeline enforces it.

## Open questions

- **KTX2 encoding.** glTF-Transform needs the native `toktx` (KTX-Software) binary for KTX2.
  The options are installing it in CI and the Docker build stage, or using resized WebP or
  PNG instead. Decide in C3.
- **Art licence.** Likely CC BY-SA 4.0 (ADR-0008). It must be decided before the first
  original art is merged, because the sidecars name it.
- **Where large assets live in production.** PLAN.md §8 suggests a mounted volume. Fine for
  C3; the hashed URLs work either way.
- **Ruleset hash and presentation.** Swapping a model reference changes the ruleset hash and
  breaks online compatibility for a purely visual change. Splitting the hash into gameplay
  and presentation parts (noted in ADR-0009) should be decided before M8.
